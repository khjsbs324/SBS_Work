# 회의록 작성·활용

## 대상과 원문

기존 회의록과 실제 평가·피드백을 먼저 읽고 현재 과정·능력단위·양식을 대조한다. 기존 회의록이 적절하면 활용하고 없으면 작성한다. 교수법만 보완하는 요청은 해당 문단에 집중하며 전체 분석이나 지원 그룹을 새로 편성하지 않는다.

기본 보완은 기존 날짜·분석 전문·개선사항 원문을 보존하고 개선사항 끝에 추가한다. 사용자가 수정·삭제를 명시한 경우에는 그 부분만 정정한다. 회의록 제외 요청은 사유를 기록한다.

## 양식과 본문

[분석 양식](../../../../희의록및지원내역/템플릿/회의록/분석.txt)과 [개선 양식](../../../../희의록및지원내역/템플릿/회의록/개선.txt)은 등록 본문의 틀이다. 분석에는 주제·목적·결과·요소별 보완 및 조치·종합 의견·건의사항을, 개선에는 조치사항과 요청된 교수법 내용을 작성한다. 실제 능력단위요소에 맞춰 요소별 항목을 반복하고 자리표시자는 모두 실제 내용으로 채운다. 근거가 없는 선택 항목은 생략한다.

- 강사가 학생의 과제와 수업을 기록하는 문체로 쓴다. 학생이 무엇을 어떻게 수행했는지, 강사가 무엇을 설명·시연·질문·피드백할지 구체적으로 적는다. 실제 실행은 “안내함·실습함·피드백함”, 향후 지도는 “지도하기로 함·점검하기로 함”으로 구분한다.
- 본문에 작성일·추가 기록일·보완 작성일·작성 구분, 사후작성 설명, T01 같은 관리 코드, 반복 주석, 자료 조회나 작업 검증 과정을 넣지 않는다. 실제 평가·재평가 일자와 수업에 필요한 전문용어는 유지한다.
- 새 분석·지원계획에서는 실제 학생을 A·B·C 세 학습지원 그룹에 나누어 명단·강점·보완점·지원활동·확인 기준을 작성한다. A는 강점 확장과 최종 검수, B는 누락 보완과 설명·결과 연결, C는 기본 역할·필수 구성·파일 대응부터 지도할 학생으로 실제 피드백에 따라 편성한다. 고정 점수 구간으로 전원을 A에 넣거나 B·C를 ‘해당 없음’으로 대체하지 않는다. 모든 평가 대상자가 중복·누락 없이 배정되었는지 확인하며, 공식 평가점수·이수 판정은 변경하지 않는다.
- 실제 참석자가 확인될 때만 참석자 항목을 작성한다. 학생의 건의가 확인되지 않으면 교사의 수업 보완 제안으로 작성하며, 가상의 건의나 참석자를 만들지 않는다.
- 이름이 섞인 피드백은 개인별 사실로 단정하지 않는다. 빈 폴더 제출 또는 피드백 부족은 파일 존재·열림·내용 확인부터 지원한다. 학생용 지원자료에는 회의록의 이름·점수를 옮기지 않는다.

## 교수법과 다음 단위 연결

현재 확인한 능력단위 종료일 순서로 연결한다. 첫 단위는 학생의 강점·보완사항과 교수법 개선을 작성하고, 이후 단위는 앞선 지도 내용에 이어 나타난 학생의 수행 변화·남은 과제, 이번 교수법 개선, 다음 단위의 후속 지도를 작성한다.

학생 이름과 구체적인 과제 결과를 활용하되 관측된 변화만 적는다. 실제 적용 근거가 없는 교수법을 과거에 실행한 것으로 바꾸거나 평균점수 차이만으로 지도 효과를 단정하지 않는다. 같은 종료일 또는 수업기간이 겹치는 단위는 공통 보완사항으로 연결한다. 아직 평가하지 않은 단위는 평가 후 확인할 항목을 준비한다. 연결 순서와 근거·미확인 사항은 로컬 기록에 남긴다.

## 재평가

현재 LMS에 재평가 대상·결과가 등록된 능력단위에만 관련 내용을 작성한다. 결석자평가와 재평가를 구분하고 대상자·인원·실시일·실시 사유를 확인한다. 본평가 미제출로 진행했다는 사실이 자료나 사용자 설명으로 확인되면 그 사유를 명확히 적는다. 현재 점수만으로 점수 미달이나 미제출 사유를 추정하지 않는다. 사유가 확인되지 않으면 로컬 미확인 항목에 남기고 단정적인 사유를 작성하지 않는다.

기존 재평가 기록은 정정 요청 범위 밖이면 보존한다. 실제 재평가 일자는 본문에 유지하고 관측 경로·확인 시각은 로컬 증빙에 기록한다. 공식 점수와 학생 제출물은 변경하지 않는다.

## 날짜와 로컬 기록

지원 게시일, LMS 회의일시, 실제 작성·정정 시각을 구분한다. 기존 회의록의 회의일시를 유지하며 신규 사후 분석 기록은 실제 작성일을 회의일시 필드에 입력한다. 그 날짜를 과거 회의 개최 사실로 설명하지 않는다. 실제 작성·정정일과 사후작성 여부는 로컬에 보관한다.

[입력 예시](../../../../희의록및지원내역/템플릿/회의록/meeting.example.json)의 analysis와 improvement만 각 본문 필드에 입력한다. meeting_date는 LMS 회의일시 필드 값이며, actual_date·retrospective·original·근거·확인 한계 등은 로컬 관리 정보다. 기존 입력과 호환되도록 actual_date를 유지한다. 예전 JSON에 meeting_date가 없으면 현재 LMS와 원본 날짜를 확인하여 결정하고 actual_date로 기존 날짜를 덮어쓰지 않는다.

01_근거자료에는 평가·피드백과 연결 근거를, 02_회의록에는 원본·작성안 및 관리 정보를, 04_등록검증에는 실제 저장 확인을 보관한다. 지원자료 전체 작업의 기준 원본은 `02_회의록/회의록.json` 하나다. 전문·meeting_date·actual_date·roster_path·groups·teaching_link를 채운다. 실제 평가 대상과 능력단위요소는 [평가대상 예시](../../../../희의록및지원내역/템플릿/회의록/평가대상.example.json)에 따라 01_근거자료에 보관한다. groups에는 실제 student_ids와 편성 근거(basis)·강점(strengths)·보완점(needs)·지원활동(activities)·확인 기준(criteria)을 작성한다. 분석과 개선 각각에 `A그룹 : [이름, 이름]` 형식의 명단을 A·B·C 모두 넣고 구조화된 명단과 맞춘다.

`meeting-check RUN`으로 구조·누락·중복을 확인한 뒤 직접 내용 검수를 한다. 반환된 meeting_sha256·roster_sha256과 실제 검토 결과를 meeting_resolved 증빙에 기록한다. 실제 LMS에서 읽은 날짜·두 본문 전문·URL·확인 시각을 readback에 담아 원본과 대조한다. 상세 필드는 [증빙규격](../../../../희의록및지원내역/스키마/증빙규격.md)을 따른다. 로컬 제작만 요청받은 경우 mode=drafted, local_reviewed=true로 검수한 실제 초안을 기록하며 exact_readback으로 저장 사실을 주장하지 않는다. 명시적 LMS 저장 제외도 로컬 회의록·편성·지원계획 검수는 필요하다.

회의록 검수 완료 후에만 `meeting-plan RUN GROUP`으로 지원계획을 읽고 자료를 작성한다. 본문만 다듬으면 회의록을 다시 검수·저장 확인하며, 그룹의 명단·지원계획이 바뀌면 영향을 받는 그룹 자료만 다시 검수한다. 기존 완료 기록에는 새 필드를 소급 입력하지 않고, 재개·정정할 때 적용한다.

## 회의록만 정정할 때

지원 게시글용 revise 명령을 회의록 정정에 사용하지 않는다. 기존 작업 폴더의 05_정정이력/정정ID/에 현재 회의록의 날짜·두 본문 전문과 URL·과정·능력단위·확인 시각, 실제 수정 요청·사유를 보존한다. 기존 작업 폴더가 없다면 정정 작업용 실행일시 폴더에 같은 구조로 보관한다. 이 경우 지원자료 전체 작업의 작업정보·진행상태를 임의로 생성하거나 기존 완료 상태를 바꾸지 않는다.

수정안과 원문을 대조한 뒤 요청 범위만 저장한다. 결과가 불명확하면 현재 값을 다시 읽어 수정 전·예상 수정 후 값과 비교한다. 수정 후 값이면 재저장 없이 확인하고, 다른 값이면 차이를 확인한 뒤 진행한다. 저장 확인 후 정정완료.json에 변경 범위·보존 확인·URL·검증 시각과 근거 파일을 남긴다.

## 검수와 저장 확인

등록 전 본문을 직접 읽고 다음을 확인한다.

- 관리용 날짜·사후작성 설명·코드·반복 주석·자리표시자가 본문에 남아 있지 않은가.
- 학생의 변화와 교수법이 구체적이며 실행 사실과 지도 계획의 시제가 맞는가.
- 종료일 순서와 다음 단위 연결, 재평가 등록 여부와 사유가 맞는가.
- A·B·C 각 그룹에 실제 학생 명단이 있고, 모든 대상자가 한 그룹씩 배정되며 그룹별 조치가 학생의 보완 요구와 맞는가.
- 요청 범위 밖 원문·회의일시·평가 및 재평가 일자가 보존됐는가.

ver4에서 관측한 경로는 appraisal/analysis/index.php?Pcode=…&Lcode=…, 수정은 appraisal/analysis/write.php?Pcode=…&Lcode=…이다. 현재 폼의 strMeetDate·strContents·strContents2와 실제 등록 버튼을 확인한다. 저장 후 수정 폼이 열린 것을 확인하고 날짜·두 본문 전문을 새로 읽어 예상값과 대조하며 상세 화면도 판독한다. 전체 지원 작업의 meeting_resolved는 이 확인 뒤 기록한다. 회의록만 정정한 작업은 별도 정정 증빙으로 완료한다. 기존 활용·제외도 사유와 확인 시각을 남긴다.
