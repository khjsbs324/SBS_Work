# 구현 응용 피드백 지침

학생 피드백은 `재현 환경 → 관찰한 코드·화면·동작 → 표준·명세·본래 의도와의 차이 → 사용자·개발 영향 → 최소 수정 범위 → 재검증 방법` 순서로 작성한다.

- 파일 경로·선택자·함수·화면 폭·상태·Console·Network·협업 이슈 ID 중 하나 이상의 직접 근거를 사용한다.
- 기능이 많다·화려하다는 표현보다 콘텐츠 활용, 표준화, 재사용성, 접근성, 성능과 오류 복구를 언급한다.
- 보고서와 실제 실행 결과가 다르면 실행 결과를 기준으로 하고 차이가 발생한 환경을 적는다.
- 같은 코드 결함으로 여러 화면에서 문제가 나면 원인 한 곳을 수정하도록 안내하고 반복 감점하지 않는다.
- 특정 프레임워크로 교체하라고 단정하지 않고 현재 구조에서 가능한 최소 수정과 구조적 개선 순서를 제시한다.
- 실제·강사 제공 협업 이슈와 코드 변경의 연결이 없으면 필요한 기록 항목과 재검증 조건을 알려준다.

예: “모바일 390px의 프로젝트 필터에서 `.filter-button`을 클릭하면 선택 표시는 바뀌지만 `aria-pressed`가 갱신되지 않아 키보드·보조기술 사용자가 현재 필터를 확인하기 어렵습니다. `setActiveFilter()`에서 시각 클래스와 `aria-pressed`를 같은 상태 값으로 갱신하고, Tab→Space 조작과 결과 목록 변경을 함께 재검증해 보세요.”

학생 공개용 피드백에는 내부 점수 계산이나 강사용 정답 전체를 포함하지 않는다.
