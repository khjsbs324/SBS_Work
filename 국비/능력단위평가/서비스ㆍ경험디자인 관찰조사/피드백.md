# 서비스ㆍ경험디자인 관찰조사 피드백 기준

## 작성 방식

학생이 실제로 제출한 PDF와 이 평가에서 증빙으로 인정한 자료를 대조하여 작성한다. 함께 제출되어 증빙으로 인정한 Markdown에 답변이 있으면 PDF의 같은 칸이 비었다는 이유만으로 누락을 단정하지 않는다. 자료 간 내용이 다르면 실제 차이와 판단에 사용한 위치를 교사용 기록에 남긴다.

[공통 피드백 작성 지침](../피드백.md)의 말투와 구성 원칙을 적용하고, 이 문서에서는 관찰조사 평가의 내용과 증빙 범위를 구체화한다. 사용자 승인에 따라 기존 지침의 `관찰 → 기준 → 판단 → 영향 → 구체적 개선`은 작성자가 근거를 검토할 때 빠뜨리지 않을 요소로 적용한다. 공개 피드백의 모든 문장·문단을 그 순서에 맞추는 고정 양식으로 사용하지 않는다.

12개 평가항목은 모두 검토하고 문항별 판단 근거는 교사용 기록에 남긴다. 학생 공개문은 학생이 먼저 수정해야 할 문제를 중심으로 구성하며, 관련된 내용은 묶어서 설명한다. 서비스 내용·문서의 정보 구조·PDF 가독성을 다루고, 과제에 해당하지 않는 코드·브라우저 피드백을 추가하지 않는다.

## 말투와 문장

- `~습니다`, `~하세요`, `~바랍니다`를 유지한다. 자연스럽게 쓰기 위해 `~해요` 말투로 바꾸지 않는다.
- 학생의 실제 기획에서 중요한 강점이나 가장 시급한 문제로 시작한다. 제출 사실 안내, 서비스 전체 요약, 의례적인 칭찬을 첫 문단의 필수 요소로 삼지 않는다.
- 기능명·수치·문장·이용 장면을 직접 짚고, 학생이 수정 위치를 찾는 데 필요하면 페이지나 절을 적는다. 모든 문장에 위치를 반복해서 붙이지 않는다.
- 강점은 학생이 선택한 내용과 그 선택이 이용 상황에 맞는 이유로 설명한다. 부족한 점은 수정할 대상·이유·방법이 드러나도록 쓴다.
- `확인됩니다`, `적절합니다`, `다만`을 매 문단 같은 자리에 반복하지 않는다. 특정 단어 자체를 일괄 금지하지 않고, 설명에 기여하지 않는 반복을 줄인다.
- `평가에 반영했습니다`, `인정했습니다` 같은 채점 처리 문구와 근거 없는 `완성도`, `설득력`, `우수합니다`로 설명을 대신하지 않는다.
- 문장과 문단의 길이는 설명할 내용에 맞춘다. 글자 수, 문단 수, 칭찬과 지적의 비율을 정하지 않는다. 필요한 설명은 충분히 쓰고 중복 요약과 분량을 채우는 문장은 삭제한다.
- 마지막에는 공개용 최종점수와 다음 수정의 우선순위를 짧게 정리한다. 앞선 장점과 문제를 모두 다시 나열하거나 `^^`를 자동으로 붙이지 않는다.

## 반드시 확인할 내용

- 서비스 설명만으로 대상·문제·이용 과정·혜택·브랜드 연결을 이해할 수 있는가.
- 자료 출처와 확인 내용, 학생 해석, 가설, AI 제안이 구분되는가.
- 라이프스타일·인구학적·소비심리학적 특성이 사용자 유형과 요구 차이를 설명하는가.
- 이용 전·중·후의 기능적·감성적·사회적 경험이 디자인 전략에 연결되는가.
- 선행자료가 관찰 질문·대상·과업·방법·시간·기록·판정 조건에 이어지는가.
- 요구 도출에 수집 자료와 이론을 각각 어떻게 적용했는가.
- 경쟁 서비스에서 자신의 서비스 개념과 차별점을 어떻게 도출했는가.
- 경험 단서에서 명시적 요구와 잠재 요구를 구별하고 대안 해석을 검토했는가.
- AI 제안을 선택·수정·보류한 이유와 실제 변경 내용이 연결되는가.
- 수정 전후, 재확인 결과와 추가 확인할 가설이 추적되는가.
- PDF 글자·표·이미지·출처가 읽히고 필요한 기록을 찾을 수 있는가.

## 근거와 판단 범위

- 가상 시나리오 자체나 실제 사용자 관찰 미실시를 개선점·감점 사유로 쓰지 않는다.
- 조사 사실, 학생의 해석, 가설, AI 제안, 수정 후 실제 확인 결과를 구분한다. 문서에 기능을 추가한 사실만으로 사용자 만족·이용 시간·성공률이 개선됐다고 단정하지 않는다.
- 출처가 필요한 문항에서 근거가 부족하면 자료명, 조사 대상, 해당 문장·표의 위치, 해석과의 연결 중 무엇이 빠졌는지 짚는다. 원문을 확인하지 못했다는 이유만으로 허위 자료라고 단정하지 않는다.
- 제출 자료의 수치가 다른 의미로 쓰였다면 어느 위치에서 뜻이 달라졌는지 설명하고 원문의 질문·대상·조건과 대조하도록 안내한다. 평가자가 새로 찾은 자료를 학생이 제출한 조사 근거로 대신 채워 넣지 않는다.
- 미확인 행동, 속마음, 수치와 사용자 반응을 대신 만들어 설명하지 않는다.
- 개선을 위한 예시나 질문은 `예를 들어`, `이런 경우를 검토하세요` 등으로 제안임을 드러낸다. 학생이 이미 작성하거나 확인한 내용처럼 서술하지 않는다.
- 근거가 타당한 보류·유지는 인정하고 모든 AI 제안을 반영하라고 요구하지 않는다.
- 빈 표나 체크박스만으로 미수행을 단정하지 않고 다른 절과 인정된 제출물의 동등한 증빙을 먼저 확인한다.
- 같은 원인의 문제는 관련 내용을 묶어 설명하고 여러 문항에서 반복 감점하지 않는다. 서로 다른 수행의 부족을 각각 판단한다면 독립된 근거를 교사용 기록에 남긴다.
- 예쁘다·성의 없다·분량이 적다 같은 인상평 대신 제출물에서 확인 가능한 차이를 쓴다.
- 문체 수정만으로 원점수·등록점수를 바꾸지 않는다. 실제 관찰, 코드 구현, 서비스 출시 등 이 평가에서 요구하지 않은 조건을 개선 조언을 통해 새 필수 요건으로 만들지 않는다.
- 내부 SO 번호, 원점수·환산식, 순위, 다른 학생의 정보, 강사용 정답·판단표와 미실행 도구 검증을 학생 공개문에 넣지 않는다. 검증된 학생 공개용 최종점수는 안내한다.

## 내용별 개선 안내

- 사용자 조사: 시장·제품 기능 자료와 사용자 집단의 생활·인구·소비심리 자료가 무엇을 설명하는지 구별한다. 이미 적은 유형의 어떤 특성에 근거가 더 필요한지 안내한다.
- 잠재 요구: 학생이 적은 행동·감정 단서에서 출발한다. 같은 행동의 가능한 다른 이유를 비교하고, 그 이유를 구분할 질문이나 확인 방법을 제안한다. 원하는 기능을 다른 말로 반복하는 데 그치지 않는다.
- 이론 적용: 분류 이름만 지적하지 않고 어떤 사용자와 상황에서 그 요구를 그렇게 분류할지, 우선순위에 어떤 차이가 생기는지 설명하도록 안내한다.
- 경쟁사 비교: 실제로 확인한 제공 내용과 학생이 예상한 불편을 나누도록 안내한다. 여러 서비스를 한 행에 묶었다면 확인한 서비스별 범위와 위치를 정리하게 한다. 확인하지 않은 기능의 부재를 대신 단정하지 않는다.
- 수정과 재확인: 수정표뿐 아니라 서비스 설명·요구표·여정·관찰 질문·성공 기준에 바뀐 내용이 일관되게 반영됐는지 대조하도록 안내한다. 확인한 위치와 결과, 남은 불일치, 앞으로 확인할 효과를 구별해 기록하게 한다.
- 관찰 계획: 서로 다른 시간·판정 조건이 어느 과업에 적용되는지, 다른 사람이 같은 방식으로 기록할 수 있는지 확인한다. 실제 수행 결과와 계획상의 목표를 혼동하지 않는다.
- PDF 표현: 실제로 읽기 어렵거나 내용이 빠진 위치를 짚고 표 분리·열 조정·질문과 답변 배치 등 필요한 수정 방법을 안내한다. 보기 좋은 편집 자체에 가산점을 주지 않는다.

## 구성과 최종 확인

주요 보완점 두세 가지를 앞에서 충분히 설명하는 것을 우선 고려하되, 개수와 문단 순서를 고정하지 않는다. 학생이 잘한 선택은 그와 관련된 설명에 자연스럽게 연결하고, PDF 표현 문제는 내용 판단과 구별해서 다룬다. 모든 학생에게 같은 항목별 문단을 복사해 사용하지 않는다.

작성 후 다음을 확인한다.

- 첫 부분에서 이 학생의 기획과 중요한 수정 방향을 알 수 있는가.
- 학생이 무엇을 어디에서 어떻게 고칠지 이해할 수 있는가.
- 근거·판단·영향·개선 방법이 필요한 만큼 설명되어 있으며 같은 문제를 반복하지 않았는가.
- 사실, 예상, 실제 확인 결과, 교사가 제안한 예시가 구별되는가.
- 평가항목을 모두 검토했으며 공개문의 분량을 줄이느라 교사용 판단 근거를 빠뜨리지 않았는가.
- 말투, 학생명·프로젝트명, 공개용 최종점수가 정확하고 내부 정보가 섞이지 않았는가.

실제 현장조사 수행의 검증 여부는 강사용 기록에서 별도로 관리한다. 이번 모의 평가의 성적만으로 현장 관찰 능력 검증 완료를 선언하지 않는다.
