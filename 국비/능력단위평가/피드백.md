# 공통 피드백 작성 지침

## 적용 범위

- 사용자의 최신 지시와 해당 평가의 전용 지침, `Exam.md` 및 채점기준을 따른다.
- 평가별 필수 제출물과 검증 범위를 먼저 확인한다. 다른 평가의 코드·화면·실제 관찰·구현·배포 조건을 가져오지 않는다.
- 문체만 수정할 때는 기존 점수와 평가 요건을 유지한다. 재확인으로 판단이 달라졌다면 근거를 확인하고 이전 설명부터 정정한다.
- 수행준거별 점수와 모든 판단 근거는 교사용 기록에 남긴다. 학생 공개문은 학생이 결과를 이해하고 다음 수정을 할 수 있도록 작성한다.

## 문체와 표현

- `~습니다`, `~하세요`, `~바랍니다`를 사용한다. 자연스럽게 고친다는 이유로 `~해요` 말투로 바꾸지 않는다.
- 학생에게 직접 설명하는 교사의 문장으로 쓴다. 짧은 판단과 필요한 설명을 섞고, 한 문장에 여러 추상적인 평가를 쌓지 않는다.
- 첫 문장을 제출 확인이나 칭찬으로 시작할 의무는 없다. 해당 학생에게 먼저 전달할 내용으로 시작한다.
- 강점은 실제로 잘한 선택과 그 이유를 짚는다. 개선점마다 칭찬을 붙여 균형을 맞추거나 장점과 지적의 비율을 정하지 않는다.
- 모든 문단을 같은 도입부나 `다만`으로 연결하지 않는다. 특정 단어 자체보다 역할 없이 반복되는 문장 구조를 줄인다.
- `평가에 반영했습니다`, `인정했습니다` 같은 채점 행정 설명보다 제출물의 어떤 부분이 왜 적절하거나 부족한지 설명한다.
- `완성도를 높이세요`, `설득력이 부족합니다`로 끝내지 않는다. 학생이 고칠 대상과 이유를 이어서 말한다.
- 근거 없는 칭찬, 성의·재능에 대한 인상평, 평가자의 취향을 정답처럼 제시하는 표현을 쓰지 않는다.
- `^^`나 이모티콘을 자동으로 붙이지 않는다. 필요한 인사는 짧게 쓰고, 앞의 내용을 다시 길게 요약하지 않는다.

## 검토 기준과 글의 구성

다음은 판단에 필요한 검토 기준이다. 모든 문장이나 문단을 이 순서로 반복해서 쓰라는 뜻이 아니다.

- 제출물에서 실제로 확인한 내용은 무엇인가.
- 학생의 목적과 해당 평가기준에 비추어 어떤 판단을 할 수 있는가.
- 그 부분이 사용자 경험이나 결과물에 어떤 영향을 주는가. 실제 확인한 영향과 예상되는 영향은 구별했는가.
- 학생이 무엇을 어떻게 고치고, 고친 뒤 무엇을 확인하면 되는가.

글은 평가항목 순서를 그대로 나열하기보다 다음 원칙에 따라 구성한다.

- 주요 개선점 2~3개를 우선 살펴보되 개수를 억지로 맞추지 않는다. 해당 학생의 결과에 가장 큰 영향을 주는 부분을 앞에서 설명한다.
- 같은 원인이나 수정 작업으로 이어지는 문제는 묶어서 설명한다. 문서의 여러 위치를 언급하더라도 동일한 지적을 반복하지 않는다.
- 학생마다 프로젝트의 실제 장면, 선택, 오류에 맞춰 설명의 순서와 비중을 달리한다.
- 필요한 강점과 보완점은 빠뜨리지 않되, 검토한 모든 수행준거를 공개 피드백의 독립 문단으로 만들지는 않는다.
- PDF 가독성, 화면, 코드 등 표현·구현 피드백은 해당 평가에 적용되고 실제로 확인한 경우에 다룬다.

## 제출 근거와 확인 범위

- 해당 평가에서 인정하는 제출물 전체를 대조한다. 특정 칸이나 PDF가 비어 있어도 다른 절·파일에 동등한 답변이 있는지 먼저 확인한다.
- 빈칸, 체크박스, 문서 길이만으로 수행 누락을 단정하거나 별도 감점하지 않는다.
- 실제 제출 장면·문장·수치·기능을 근거로 설명한다. 학생이 수정 위치를 찾는 데 도움이 될 때 페이지·절·파일·화면 위치를 붙인다.
- 인용은 판단에 필요한 짧은 부분을 사용한다. 모든 문단에 인용이나 쪽 번호를 넣는 횟수 규칙은 두지 않는다.
- 조사 사실, 학생의 해석, 가설, AI 제안을 구별한다. AI 답변은 그 자체로 조사 출처가 되지 않는다.
- 출처는 이름이나 링크의 존재뿐 아니라 확인한 내용, 조사 대상·조건, 학생의 적용 범위가 맞는지 살핀다.
- 출처를 확인하지 못했다면 확인에 필요한 정보와 현재의 한계를 적는다. 검색되지 않는다는 이유로 허위·조작이라고 단정하지 않는다.
- 문서에 기능을 추가한 사실과 그 기능의 실제 동작, 사용자에게 나타난 효과를 구별한다. 확인한 범위를 넘겨 통과나 효과 달성을 선언하지 않는다.
- 평가자가 제시하는 개선 예시는 앞으로 검토할 제안임을 밝힌다. 학생이 이미 수행한 행동이나 실제 사용자 반응처럼 쓰지 않는다.
- 다른 학생의 정보나 결과를 가져와 해당 학생의 근거로 사용하지 않는다.

## 실행할 수 있는 개선 안내

- 개선할 대상과 이유를 연결하고, 학생이 바로 착수할 수 있는 수정 방법을 제시한다.
- 수치나 자료 해석이 문제라면 어떤 원문·대상·조건을 대조해야 하는지 구체적으로 적는다.
- 기능이나 절차가 문제라면 어디에서 무엇을 선택하고 어떤 안내나 결과로 이어져야 하는지 설명한다.
- 요구 해석이 문제라면 제출된 행동 단서에서 가능한 이유를 나누고, 이를 구별할 질문이나 확인 방법을 제안한다.
- 재확인이 부족하다면 수정한 위치와 확인 조건을 대조하게 한다. 실제 동작·효과 검증이 필요한지는 해당 평가의 요구 범위에 따른다.
- AI 제안을 모두 반영하게 하지 않는다. 선택·수정·보류·유지한 이유와 실제 반영 결과를 살핀다.
- 개선을 위해 새 기능이나 제출물을 무조건 늘리게 하지 않는다. 기존 내용의 정정·정리·범위 축소로 해결할 수 있는지도 살핀다.

## 분량과 마무리

- 최대한 길게 쓰기보다 학생이 수정할 대상·이유·방법을 이해할 만큼 구체적으로 쓴다.
- 같은 근거, 주의사항, 칭찬, 다음 과제를 반복한 문장은 삭제한다. 설명의 깊이는 문제의 중요도와 복잡성에 맞춘다.
- 글자수, 문단수, 문단 길이, 칭찬과 지적의 비율을 고정하지 않는다. 같은 형태의 글을 학생마다 반복하지 않는다.
- 작성 예시는 표현을 이해하기 위한 참고로만 사용한다. 학생명과 과제명만 바꾸어 채우는 복사 양식으로 사용하지 않는다.
- 마지막에는 공개 가능한 최종점수와 다음 작업의 우선순위를 짧게 안내한다. 전체 장단점과 점수 산정 과정을 다시 길게 나열하지 않는다.

- 추상적인 설명: “수정 전후의 연결성이 부족하여 기획의 완성도를 제한합니다. 재확인 과정을 보완하시기 바랍니다.”

## 공개 전 확인

- 학생명·프로젝트명·최종점수와 실제 제출 근거가 해당 학생의 결과와 일치하는가.
- 지적한 내용이 다른 인정 제출물에서 이미 답변된 것은 아닌가.
- 같은 원인을 반복 지적하거나 여러 문항에서 중복 감점하지 않았는가. 서로 다른 결함이라면 교사용 기록에서 판단 대상을 구분했는가.
- 확인한 사실과 해석·가설·추가 제안이 구별되고, 수정할 위치와 방법을 학생이 찾을 수 있는가.
- 내부 원점수·환산식·배분 방식·내부 문항 코드·순위·다른 학생 정보·강사용 정답이 공개문에 섞이지 않았는가.
- 문체 수정 과정에서 점수를 바꾸거나 해당 평가에 없는 필수 요건을 추가하지 않았는가.
- 불필요한 행정 문구와 반복을 덜어냈으며, 학생에게 직접 설명하는 공식적인 말투를 유지했는가.
