# 구현 평가 피드백 기준

## 목적

피드백은 효과의 수나 특정 프레임워크 사용 여부를 평가하지 않는다. 학생의 설계 자료가 실행 가능한 콘텐츠와 기능으로 연결되고, 개발 협업의 전달·협의 결과가 최종 구현에 반영됐는지를 직접 증빙으로 설명한다.

## 작성 원칙

1. 제출 ZIP, 보고서 PDF와 실제 브라우저에서 확인한 내용만 근거로 쓴다.
2. 실행하지 못한 기능을 정상 작동한다고 추측하지 않는다.
3. `관찰 → 설계·의도 대조 → 매체 적합성 → 영향 → 수정·재검증 방법` 순서로 작성한다.
4. 코드 스타일 자체보다 콘텐츠 구조, 화면 흐름, 기능 동작과 유지 가능한 전달 정보를 우선한다.
5. 오류가 하나의 원인에서 발생했다면 여러 문항에서 반복 감점하지 않는다.
6. 실제 검토 의견, 강사 제공 시나리오와 학생이 가정한 내용을 구분한다.
7. 외부 배포 미실시, 특정 라이브러리 미사용 또는 평가자 취향만으로 감점하지 않는다.
8. 개선 방법은 파일·화면·선택자·기능 ID·브라우저 조건처럼 학생이 다시 확인할 수 있게 구체화한다.
9. 마지막에는 전체 장점, 핵심 보완점과 점수 산정 이유를 정리한다.
10. 내부 환산식, 순위와 다른 학생의 정보는 공개하지 않는다.

## 반드시 다룰 내용

- 정보구조와 콘텐츠 우선순위가 실제 화면에 반영된 상태
- 핵심 과업의 시각적 흐름과 링크·내비게이션
- 멀티미디어·상호작용 기능의 필요성과 기술 제안
- 데스크톱·모바일 등 선택한 매체 환경에서의 구현 상태
- HTML·CSS·JavaScript와 자산의 실행 가능성
- 기능 오류, 키보드 사용, 대체 텍스트, 로딩과 성능 점검
- 개발 전달 문서의 명확성과 코드·화면 연결
- 협의한 이슈의 반영·보류·제외 근거와 최종 재검증
