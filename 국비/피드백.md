# 구현 응용 채점 및 피드백 파이프라인

> 용도: HTML·CSS·JavaScript·Git·GitHub 범위의 NCS `구현 응용` 학생 제출물을 동일한 절차로 채점하고, 점수 근거와 화면 피드백을 빠짐없이 남기기 위한 강사용 실행 규약이다.

## 1. 채점 원칙

1. **수행준거 수를 고정한다.** 입력된 수행준거 1개를 채점 문항 1개로 사용한다. 수행준거를 임의로 합치거나 나누거나 삭제하지 않는다.
2. **절대평가를 먼저 한다.** 학생의 코드·화면·Git 기록·문서에서 확인한 증빙으로 원점수를 확정한다. 다른 학생의 점수나 순위로 원점수를 만들지 않는다.
3. **원점수와 등록점수를 모두 정수로 관리한다.** 전체 등록점수는 `ROUND(60 + (원점수 × 0.4), 0)`으로 확정한다. 문항별 이상적 환산값은 `문항 배점 × 0.6 + 문항 원점수 × 0.4`로 계산하되 중간값으로만 사용하고, 최대잔여법으로 정수 배분하여 문항 합계와 전체 등록점수를 일치시킨다.
4. **각 문항마다 독립적인 4단계 기준을 사용한다.** 하나의 공통 등급표를 모든 문항에 반복 적용하지 않는다.
5. **완성 화면만으로 채점하지 않는다.** 정확한 코드, 불필요한 코드 여부, 웹표준, 시맨틱 구조, 접근성, 상호작용, 협업 가능성, 검증 기록을 함께 본다.
6. **대체 구현을 인정한다.** 정답 코드와 선택자나 작성 순서가 달라도 요구 동작과 품질 기준을 충족하면 인정한다.
7. **같은 결함을 중복 감점하지 않는다.** 하나의 원인이 여러 증상을 만들었다면 주 문항에서 감점하고, 다른 문항에는 영향만 기록한다. 서로 다른 수행준거를 실제로 각각 침해한 경우에만 중복 반영하고 이유를 밝힌다.
8. **확인하지 못한 사실을 추측하지 않는다.** 학생이 필수 증빙을 제출하지 않은 경우와 평가 환경 문제로 확인하지 못한 경우를 구분한다.
9. **학생별 화면 피드백을 반드시 제공한다.** 이미지 또는 화면 검토 결과가 없으면 그 사유를 명시한다. 코드 점수만 제시하고 화면 피드백을 생략하지 않는다.
10. **강사용 정답을 학생 피드백에 그대로 노출하지 않는다.** 문제 원인, 영향, 수정 방향은 제시하되 전체 정답 코드를 복사하지 않는다.

## 2. 자료 우선순위와 입력 계약

자료가 충돌하면 다음 순서로 판단한다.

1. 사용자의 최신 채점 지시
2. 해당 과제의 문제 코드와 정답 코드
3. 해당 NCS 원본 PDF 중 `구현 응용` 수행준거
4. 과제 안내, 목표 이미지, 기능 요구사항, 채점기준 예시
5. 학생 제출 코드, 저장소, 배포 URL, README 및 증빙
6. 기존 채점 결과와 학급 내 상대 순위

채점 시작 전에 아래 입력을 확인한다.

- 과제명, 학생명 또는 팀명, 제출 시각
- 평가 대상 수행준거 원문과 개수
- 문제 코드, 정답 코드, 목표 이미지
- 학생 소스 압축 파일 또는 폴더
- GitHub 저장소 URL과 배포 URL
- README, 작업 설명, 코드 주석, 테스트 또는 캡처 자료
- 요구 브라우저와 화면 너비

입력 누락 처리:

- 학생이 제출해야 하는 저장소·배포·문서가 없으면 관련 문항에서만 미제출로 처리한다.
- 평가자의 서버, 권한, 압축 해제 또는 네트워크 문제로 열지 못한 자료는 0점으로 단정하지 않고 `평가 보류`로 기록한다.
- 서로 다른 과제의 문제 코드·정답·루브릭을 섞지 않는다.

### 3.2 수행준거가 다른 경우

1. 수행준거를 입력 순서대로 `C-01`부터 번호를 붙인다.
2. 문항 수가 수행준거 수와 같은지 확인한다.
3. 각 문항 중요도를 `상=3`, `중=2`, `하=1`로 정한다. 중요도는 필수 동작, 표준·접근성, 코드 정확성, 협업 증빙 순으로 판단하고 근거를 남긴다.
4. `100 × 문항 중요도 ÷ 전체 중요도 합`으로 1차 배점을 계산한다.
5. 소수점 이하는 버리고, 남은 점수는 소수점이 큰 문항부터 1점씩 배정한다. 동률이면 수행준거 원문 순서를 따른다.
6. 최종 배점이 모두 정수이며 합계가 100인지 확인한다.
7. 각 문항에 해당 작업에서 실제로 확인할 증빙과 문항별 4단계 점수 구간을 작성한다. 비율 계산은 초안 작성에만 사용하고, 최종 기준은 구체적인 요소와 동작으로 표현한다.

다음 검증을 통과하기 전에는 학생 채점을 시작하지 않는다.

```text
수행준거 수 = 채점 문항 수
문항별 배점 = 정수
문항별 4단계 점수 구간에 빈 점수 없음
문항별 최고점 = 해당 문항 배점
전체 배점 합계 = 100
```

### 3.3 기본 9개 문항의 4단계 기준

아래 기준은 공유 대화의 아파트 홍보 웹 페이지 과제에 바로 적용하는 기본 프로필이다. 다른 주제의 구현 응용 과제에서는 `브랜드명`, `문의 요소`, `상단바` 같은 과제별 명사를 새 요구사항의 실제 요소로 바꾸되, 수행준거 수와 배점을 임의 변경하지 않는다.

#### CA-01. 전체 콘텐츠 구조 구성 — 10점

| 점수 | 판정 기준 |
|---:|---|
| 8~10 | 브랜드명 또는 로고, 주요 메뉴, 전화번호 또는 문의 요소, 메뉴 버튼, 이미지 영역, 본문 콘텐츠가 과제의 정보 구조에 맞게 모두 구성되었다. |
| 5~7 | 주요 콘텐츠는 대부분 있으나 메뉴명, 문의 정보, 이미지 영역, 본문 중 일부의 구성이나 위치가 부족하다. |
| 3~4 | header와 본문 구조는 있으나 목적과 역할 구분이 불명확하고 일부 필수 콘텐츠가 빠져 있다. |
| 0~2 | 전체 구조를 파악하기 어렵거나 필수 콘텐츠 대부분이 구현되지 않았다. |

#### CA-02. 시각적인 흐름과 위계 — 8점

| 점수 | 판정 기준 |
|---:|---|
| 7~8 | 로고, 메뉴, 문의 정보, 이미지, 본문의 읽는 순서가 자연스럽고 정렬·간격·크기·텍스트 위계가 정보 흐름에 맞다. |
| 5~6 | 전체 흐름은 적절하나 일부 정렬, 여백, 크기 또는 텍스트 간격이 불안정하다. |
| 3~4 | 콘텐츠 순서는 유지되었으나 시각적 위계와 정렬이 약해 정보를 순서대로 이해하기 어렵다. |
| 0~2 | 배치가 무질서하거나 로고, 메뉴, 본문 정보의 흐름이 불분명하다. |

#### CA-03. 멀티미디어 기능 요소의 역할과 활용 — 8점

| 점수 | 판정 기준 |
|---:|---|
| 7~8 | 메뉴 링크, 전화번호 링크, 문의 버튼, 메뉴 버튼, 이미지 영역의 역할이 구조에서 명확하고 조작 요소로 활용 가능하다. |
| 5~6 | 주요 기능 요소는 대부분 구현되었으나 일부 역할 구분이나 연결 구조가 부족하다. |
| 3~4 | 링크와 버튼은 있으나 역할이 불명확하고 단순 텍스트나 `div` 중심인 부분이 많다. |
| 0~2 | 기능 요소가 대부분 누락되었거나 메뉴·링크·버튼·이미지를 개발 요소로 확인하기 어렵다. |

#### FE-01. 웹표준과 시맨틱 구조 — 18점

| 점수 | 판정 기준 |
|---:|---|
| 15~18 | `DOCTYPE`, `lang`, `charset`, `viewport`가 정확하고 `header`, `nav`, `main`, `section`, 제목, 목록, 링크, 버튼을 의미에 맞게 사용했다. 이미지 대체텍스트, 역할 구분, 제목 계층도 적절하다. |
| 10~14 | 기본 구조와 주요 시맨틱 태그는 있으나 일부 태그 의미, 제목 계층, 대체텍스트 또는 링크·버튼 구분이 부족하다. |
| 5~9 | HTML은 작성되었으나 `div` 중심이고 시맨틱 태그 사용이 제한적이며 웹표준 요소 일부가 누락되었다. |
| 0~4 | 문서 기본 구조가 불완전하거나 시맨틱 태그를 거의 사용하지 않았다. |

#### FE-02. 웹 접근성과 사용자 조작 상태 — 12점

| 점수 | 판정 기준 |
|---:|---|
| 10~12 | 의미 있는 대체텍스트와 조작 요소의 접근 가능한 이름이 있고, 링크와 버튼의 역할이 구분된다. hover·focus·키보드 상태가 요구 동작과 일치한다. |
| 7~9 | 대체텍스트, 버튼 설명, hover 또는 focus가 일부 반영되었으나 일부 요소는 보완이 필요하다. |
| 4~6 | 이미지·버튼·링크는 있으나 접근성 속성이나 조작 상태 표현이 부족하다. |
| 0~3 | 대체텍스트, 조작 요소 이름, 역할 구분, 상태 표현이 대부분 누락되었다. |

#### FE-03. 정확하고 불필요한 코드가 없는 구현 — 20점

| 점수 | 판정 기준 |
|---:|---|
| 17~20 | HTML·CSS와 필요한 JavaScript의 책임이 구분되고 경로가 정확하다. Flex 또는 Grid를 목적에 맞게 사용했으며 미사용 선택자·빈 태그·중복 규칙·사장 코드가 거의 없다. 과도한 `position`, 고정 높이, margin, `br`, 인라인 스타일 없이 읽기 쉬운 구조이다. |
| 11~16 | 기본 구조와 레이아웃은 적절하나 일부 중복 코드, 불필요한 선택자, 경로 오류 가능성 또는 과도한 보정값이 있다. 유지보수에는 큰 문제가 없다. |
| 5~10 | 구현은 되었으나 레이아웃 방식이 불안정하고 중복·미사용 코드가 많으며 위치와 여백 값으로 화면을 억지로 맞춘 부분이 많다. |
| 0~4 | 스타일 또는 기능 적용이 거의 없거나 코드 구조가 불완전하여 정상 표시·동작하지 않고 유지보수가 어렵다. |

#### CO-01. GitHub 파일 관리와 배포 — 8점

| 점수 | 판정 기준 |
|---:|---|
| 7~8 | 저장소와 배포 URL이 모두 정상이며 파일 구조, 경로, 파일명이 협업 가능한 상태로 정리되었다. |
| 5~6 | 저장소 또는 배포는 확인되나 파일 구조, 파일명, 업로드 상태 중 일부가 정리되지 않았다. |
| 3~4 | 파일 제출은 되었으나 GitHub 관리 상태가 부족하거나 배포 확인이 어렵고 폴더 구조가 불안정하다. |
| 0~2 | 저장소, 배포, 파일 관리 증빙을 확인하기 어렵다. |

#### CO-02. 코드 주석과 문서화 — 8점

| 점수 | 판정 기준 |
|---:|---|
| 7~8 | 주석이 주요 영역의 역할과 의도를 전달하고 README 또는 제출 설명에 작업 의도, 범위, 파일 구조가 정리되었다. |
| 5~6 | 주요 설명은 있으나 일부 코드 영역의 역할이 빠졌거나 README가 간단하다. |
| 3~4 | 주석과 문서가 제한적이어서 구조와 작업 의도를 충분히 파악하기 어렵다. |
| 0~2 | 주석과 README가 없거나 협업에 필요한 설명을 확인할 수 없다. |

#### CO-03. 최종 검토와 결과 정리 — 8점

| 점수 | 판정 기준 |
|---:|---|
| 7~8 | 깨진 이미지·링크, CSS 미적용, 콘솔 오류, 테스트 문구, 불필요한 코드가 남지 않았고 지정 화면에서 안정적이며 과제 의도와 결과가 일치한다. |
| 5~6 | 결과물은 제출되었으나 일부 간격, 정렬, 경로, 링크 또는 코드 정리가 필요하다. |
| 3~4 | 기본 구현은 있으나 최종 검토가 부족해 깨진 자산, 링크·스타일 오류 또는 테스트용 내용이 남아 있다. |
| 0~2 | 결과물이 미완성이거나 브라우저에서 정상 확인하기 어렵고 최종 검토 증빙이 없다. |

## 4. 실행 파이프라인

### 0단계. 채점 매니페스트 작성

학생별 검토 전에 다음 항목을 한 번 고정한다.

```yaml
assignment: 과제명
scope: HTML, CSS, JavaScript, Git, GitHub
criteria_count: 수행준거 수
rubric_total: 100
required_viewports: [과제 지정 너비]
required_interactions: [과제 지정 동작]
required_submission: [소스, 저장소, 배포, 문서]
reference_files: [문제 코드, 정답 코드, 목표 이미지]
```

과제에서 너비를 지정하지 않았다면 기본 검토 너비는 `1920px`, `1600px`, `1024px`, `768px`, `480px`로 한다. 공유 대화의 상단바 과제처럼 별도 조건이 있으면 해당 조건을 우선한다.

### 1단계. 제출물 접수와 보존

1. 학생명과 제출 파일을 연결한다.
2. 원본을 수정하지 않고 검토용 사본에서 압축을 해제한다.
3. 파일 목록, 확장자, 주요 폴더, 시작 HTML을 기록한다.
4. 저장소 URL과 배포 URL의 접속 여부를 각각 확인한다.
5. 토큰, 비밀번호, 실제 개인정보가 포함되어 있으면 노출하지 않고 별도 위험으로 기록한다.
6. 학생 수와 제출물 수가 다르면 누락 학생을 먼저 확정한다.

### 2단계. 정적 코드 검토

#### HTML

- `DOCTYPE`, `html lang`, `meta charset`, `viewport`
- `header`, `nav`, `main`, `section`, 제목, 목록 등 의미에 맞는 구조
- 링크와 버튼의 역할 구분
- 이미지 `alt`, SVG 이름, 폼의 레이블
- 제목 계층과 DOM 읽기 순서
- 잘못 닫힌 태그, 빈 태그, 임시 텍스트, 깨진 상대 경로

#### CSS

- 파일 연결 순서와 경로
- Flex 또는 Grid 사용 목적의 적절성
- hover뿐 아니라 focus 상태 제공 여부
- 반응형 분기점과 가로 스크롤
- 과도한 고정 높이·margin·position·`br`·인라인 스타일
- 사용하지 않는 선택자, 중복 선언, 무효 선언, 지나치게 높은 명시도

#### JavaScript

- 요구된 기능의 상태 변경과 이벤트 연결
- 키보드 조작, Escape, 포커스 이동·복귀
- ARIA 상태와 실제 화면 상태의 일치
- 콘솔 오류, 존재하지 않는 요소 참조, 중복 이벤트
- 사용하지 않는 함수·변수·주석 처리된 사장 코드

`불필요한 코드`는 취향이 아니라 증빙으로 판정한다. 실제로 참조되지 않는 클래스·ID, 중복 규칙, 도달 불가능한 코드, 같은 효과를 반복하는 선언처럼 확인 가능한 항목만 감점 근거로 사용한다.

### 3단계. 브라우저 화면과 상호작용 검토

1. 학생 결과물을 로컬 정적 서버 또는 제출된 배포 URL로 연다.
2. 지정한 모든 화면 너비에서 전체 화면 캡처를 만든다.
3. 목표 이미지가 있으면 같은 너비에서 나란히 비교한다.
4. Network에서 HTML·CSS·JavaScript·이미지의 `404`를 확인한다.
5. Console 오류를 확인한다.
6. 마우스와 키보드로 모든 필수 상호작용을 각각 검증한다.
7. 축소 화면에서 겹침, 잘림, 가로 스크롤, 읽기 순서, 터치 가능한 크기를 확인한다.

상단바 과제라면 다음은 요구사항에 포함된 경우에만 확인한다.

- 견본주택 개관 중 요소의 hover 반전 색상
- 오른쪽 메뉴 아이콘의 SVG 구현과 접근 가능한 이름
- 1차 메뉴 hover/focus의 밑줄
- 1차 nav 영역에서 2차 메뉴 표시
- 2차 메뉴 항목에서 3차 메뉴 표시
- 활성 항목의 글자색·밑줄과 이미지 일치

디자인 자유도가 있는 과제는 색상이나 장식의 단순 취향 차이를 감점하지 않는다. 정보 구조, 위계, 정렬 안정성, 읽기 쉬움, 요구 동작, 접근성을 평가한다.

### 4단계. GitHub와 협업 증빙 검토

- 저장소와 배포 URL이 모두 정상인지 확인한다.
- 파일·폴더명이 협업자가 이해할 수 있고 대소문자 경로가 배포 환경에서도 맞는지 확인한다.
- 커밋이 기능 또는 수정 단위로 나뉘고 메시지가 변경 이유를 설명하는지 확인한다.
- README에 작업 의도, 구현 범위, 파일 구조, 실행 방법, 알려진 문제가 있는지 확인한다.
- 주석은 코드가 무엇을 하는지 반복하는 양이 아니라, 영역 경계·의도·협업상 주의점을 전달하는 질로 평가한다.
- PR·이슈가 요구된 과제에서만 해당 증빙을 필수로 본다.

### 5단계. 문항별 채점

각 문항을 아래 순서로 판정한다.

1. 수행준거 원문을 읽는다.
2. 해당 문항의 필수 증빙을 모두 모은다.
3. 관찰 사실과 요구사항의 차이를 적는다.
4. 4단계 기준 중 해당 구간을 선택한다.
5. 같은 구간 안에서는 충족한 핵심 요소 수, 오류 영향, 재현 빈도로 정수 점수를 정한다.
6. 점수 옆에 파일·선택자·화면 너비·동작·Git 기록 중 최소 하나의 직접 근거를 적는다.
7. 감점 원인이 다른 문항에서 이미 반영되었는지 확인한다.

점수 행의 필수 형식:

| 문항 ID | 배점 | 원점수 | 등록점수 | 직접 증빙 | 판단 및 감점 근거 |
|---|---:|---:|---:|---|---|
| CA-01 | 10 | 0~10 | 환산식 적용 | `index.html`, 화면 캡처 | 관찰한 사실과 기준 구간 |

`대체로 좋음`, `완성도가 낮음`처럼 재현할 수 없는 표현만으로 점수를 주지 않는다.

### 6단계. 학생별 화면 피드백 작성

화면 피드백은 학생마다 최소 1개 이상 작성한다. 문제가 없으면 `양호` 근거를 남긴다.

| 피드백 ID | 증빙 이미지 | 화면 너비·상태 | 관찰 | 코드 원인 | 수정 방향 | 우선순위 |
|---|---|---|---|---|---|---|
| VIS-01 | 캡처 파일 또는 링크 | 예: 1024px, 1차 nav hover | 실제 화면 차이 | 관련 파일·선택자 | 정답 전체가 아닌 개선 방향 | 상·중·하 |

화면 캡처를 얻지 못한 경우에도 이 절을 삭제하지 않고 아래처럼 적는다.

```text
화면 피드백 보류: 배포 URL 접속 실패로 브라우저 렌더링을 확인하지 못함.
확인한 정적 증빙: 파일 및 선택자
재검토에 필요한 자료: 정상 배포 URL 또는 실행 가능한 소스
```

### 7단계. 사이트 등록용 코드 비교형 피드백 작성

사이트의 `이곳에 피드백을 입력하세요.`에는 짧은 총평만 넣지 않고, 학생이 코드를 보며 바로 수정할 수 있는 비교형 피드백을 작성한다. 해당 학생의 주요 결함 3~7개를 영향도 순서로 선정하며 사소한 스타일 차이를 억지로 늘리지 않는다.

각 결함은 다음 형식을 그대로 사용한다. 사이트 상세 페이지의 예시와 같은 표시를 위해 언어명은 한 줄로 쓰고, 사이트 입력 본문에는 코드 펜스와 인라인 표기를 포함한 Markdown 백틱 문자를 넣지 않는다.

````text
1. [결함 제목]

html
<!-- 학생 코드 -->
[학생이 실제 제출한 최소 관련 코드]

html
<!-- 정답 코드 -->
[해당 결함을 고치는 데 필요한 최소 기준 코드]

피드백:
[관찰 사실 → 요구사항과의 차이 → 화면·기능·접근성 영향 → 수정 방향]
````

- HTML은 `html`, CSS는 `css`, JavaScript는 `javascript`, 문서·Git 기록은 `text`라는 언어명 한 줄을 코드 바로 앞에 쓴다.
- 학생 코드는 저장소에서 확인한 내용을 그대로 인용하고 오탈자까지 임의로 고치지 않는다.
- 정답 코드는 해당 결함에 필요한 최소 줄만 제시한다. 파일 전체, 완성 페이지 전체 또는 강사용 정답 전체를 복사하지 않는다.
- 대체 구현이 정답과 달라도 요구 동작을 만족하면 오답 비교로 만들지 않는다.
- 코드가 아예 없으면 `<!-- 학생 코드: 해당 구조 없음 -->`으로 표시하고 필요한 최소 구조만 제시한다.
- 파일 경로, 선택자, 속성, 화면 너비 또는 동작 조건을 피드백 문장에 포함한다.

결함별 비교 다음에는 표제 없이 아래 5개 문단을 이어서 작성한다.

1. 완성한 영역과 잘한 점을 구체적으로 설명한다.
2. 미완성 영역과 정확도가 낮아진 구조적 이유를 설명한다.
3. 같은 과제를 빠르게 구현할 수 있는 작업 순서를 제안한다.
4. 한 부분을 정확히 만든 뒤 반복·응용하는 방법과 재검증 방법을 안내한다.
5. 전체 방향을 긍정적으로 정리하고 다음 개선점을 압축한 뒤 자연스러운 격려 문장으로 마무리한다. 예시 톤에 맞는 경우 `고생하셨습니다^^`를 사용할 수 있다.

사이트 입력용 피드백은 학생별 실제 코드와 증빙에 맞춰 새로 작성한다. 다른 학생의 결함 목록이나 종합 문단을 이름만 바꾸어 재사용하지 않는다.

학생이 보는 사이트 입력용 피드백에는 다음 내부 평가 정보를 작성하지 않는다.

- 원점수, 등록점수 또는 총점
- `60~100점` 같은 환산 범위와 환산 공식·과정
- 통과 여부, 순위 또는 내부 채점 판단

점수 정보는 학생별 내부 결과표와 사이트 점수 입력란에만 보존한다. 마지막 종합 문단에는 개선 방향과 격려만 작성하며 `증빙 기반 원점수는 …`, `환산 최종점수는 …` 같은 문장을 넣지 않는다.

### 8단계. 원점수와 60~100점 등록점수 확정

```text
원점수 = 모든 문항 원점수의 합
정수 등록총점 = ROUND(60 + (원점수 × 0.4), 0)
문항별 이상적 환산값 = 문항 배점 × 0.6 + 문항 원점수 × 0.4
문항별 정수 등록점수 = 이상적 환산값을 내림한 뒤 최대잔여법으로 배분
```

- 원점수 0점은 등록점수 60점, 원점수 100점은 등록점수 100점이다.
- 먼저 모든 문항의 이상적 환산값을 내림하고, `정수 등록총점 - 내림값 합계`만큼 소수 나머지가 큰 문항부터 1점씩 더한다.
- 소수 나머지가 같으면 문항 ID가 앞선 문항을 우선하며, 문항별 정수 등록점수는 문항 만점을 초과할 수 없다.
- 원점수와 정수 등록점수를 학생별 결과 파일에 함께 남기고, 사이트에는 문항별 정수 등록점수만 입력한다.
- 통과 여부는 사이트 커트라인과 환산 등록점수를 기준으로 기록하되, 미해결 결함은 점수와 별도로 피드백에 명시한다.
- 등록점수가 같아도 수행준거별 강점과 결함이 다르면 피드백을 동일하게 복사하지 않는다.

### 9단계. 학급 단위 보정은 별도 수행

모든 학생의 절대평가 원점수가 확정된 뒤에만 학급 분포를 검토한다.

- 원점수 순위와 구현 단계는 채점 일관성을 점검하는 참고자료이다.
- 목표 인원수에 맞춰 원점수를 임의 조정하지 않는다. 60~100점 등록점수는 모든 학생에게 동일한 고정 환산식만 사용한다.
- 특정 인원 분포의 상대평가를 사용자가 명시적으로 요구한 경우 `원점수`와 `조정점수`를 별도 열로 보존하고, 조정 공식·구간·학생 수·변경 사유를 공개한다.
- 요청한 구간별 인원 합계가 실제 학생 수와 다르면 임의 조정하지 않고 불일치를 먼저 보고한다.
- 코드 재검토 없이 기존 총점 순위만으로 조정한 결과는 `재채점`이 아니라 `상대 배점 조정`으로 표시한다.

### 10단계. 최종 품질 검증

- [ ] 수행준거 수와 문항 수가 같다.
- [ ] 문항별 배점 합계가 100점이다.
- [ ] 각 문항에 해당 작업의 구체적인 4단계 기준이 있다.
- [ ] 모든 학생에게 모든 문항의 배점과 취득점이 있다.
- [ ] 모든 취득점에 직접 증빙 또는 미확인 사유가 있다.
- [ ] 학생별 총점 계산이 맞다.
- [ ] 동일 결함을 설명 없이 중복 감점하지 않았다.
- [ ] 모든 학생에게 화면 피드백 또는 화면 검토 보류 사유가 있다.
- [ ] 사이트 입력용 피드백에 주요 결함별 학생 코드·최소 정답 코드·구체적인 피드백이 있다.
- [ ] 코드 비교 뒤에 완성 영역, 미완성 영역, 빠른 구현 순서, 응용·재검증, 격려를 포함한 5개 종합 문단이 있다.
- [ ] 사이트 입력용 피드백에 원점수·등록점수·총점·환산 범위·환산식·통과 여부·순위가 없다.
- [ ] 저장소와 배포 URL을 혼동하지 않았다.
- [ ] 정답과 학생 코드를 파일 단위뿐 아니라 동작 단위로 비교했다.
- [ ] 학생 피드백에 강사용 정답 전체가 노출되지 않았다.
- [ ] 학생 수, 결과 파일 수, 결과표 행 수가 같다.
- [ ] 한글이 UTF-8로 정상 표시되고 파일·이미지 링크가 실제로 존재한다.

## 6. 실행 금지 사항

- 수행준거 9개를 8개 또는 14개로 임의 변경
- 학생 한 명의 점수 또는 피드백 누락
- 목표 이미지와 픽셀 단위로 다르다는 이유만으로 디자인 자유 영역 감점
- 브라우저 확인 없이 `정상 동작`으로 기록
- 저장소를 열지 않고 GitHub 협업 점수 부여
- 캡처가 있는데도 화면 피드백 생략
- 기존 순위만으로 새 점수를 만든 뒤 `재채점`이라고 표현
- 요구되지 않은 백엔드, 데이터베이스, 서버 또는 프레임워크를 평가 항목에 추가
- 수행하지 않은 테스트를 통과로 기록
